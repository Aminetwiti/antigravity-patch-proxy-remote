## 3. Findings détaillés

### 🔴 F1 — Backend Google totalement injoignable (160×)

**Symptôme**
```
http_helpers.go:291] Failed to make code assist backend request (listExperiments):
{"error":{"message":"Proxy forwarding failed: connect ETIMEDOUT 172.217.16.46:443"}}
```

**End-points en échec** : `listExperiments`, `loadCodeAssist`, `fetchUserInfo`, `recordCodeAssistMetrics`, `fetchAvailableModels`.

**Tentatives échouées en rafale** : ex. 14:32:06 → 30+ erreurs de `Failed to refresh cache in background` en moins d'1 s (le singleflight cache ne récupère jamais).

**Hypothèses**
1. Perte de connectivité vers `172.217.16.46` (host Google asia-équin ?) — traceroute/net check côté hôte.
2. Le proxy MITM local injecté (`Start Antigravity MITM.bat`) ne relaie pas correctement vers l'amont — voir `proxy-runner.js`, `start_mitm_443.ps1`.
3. Règle firewall / VPN modifié.

**Impact** : expériences, métriques, infos utilisateur : aucun rafraîchissement possible. Le système tourne donc sur un cache stale qui se vide progressivement.

### 🔴 F2 — Modèles placeholders introuvables (59×)

**Modèle concernés** : `MODEL_PLACEHOLDER_M35`, `M36`, `M50`, `M71` (4 clés distinctes).

**Symptômes en cascade**
```
interceptor.go:74] GetSlashCommands: failed to resolve cascade config:
  unknown model key MODEL_PLACEHOLDER_M50: model not found
log.go:398] failed to construct executor:
  unknown model key MODEL_PLACEHOLDER_M71: model not found
log.go:398] error executing cascade step:
  failed to resolve subagent model: no valid model found in FetchAvailableModels …
```

**Cause racine probable**
- `FetchAvailableModels` est lui-même en échec (voir F1) → la réponse est vide / partielle.
- Le code injecte des `MODEL_PLACEHOLDER_M*` (Coinbase / Claude / etc.) via `customModelStore.ts` (vu dans le workspace), mais le routeur cascade ne sait pas les retrouver quand la liste canonique n'est pas chargée.
- Reproduction d'un comportement documenté dans `antigravity-preload-duplication.md` : **refactor incomplet** entre l'API surface et le callsite.

**Impact** : Slash commands Cascade, génération streaming, subagent invocation. C'est **bloquant** pour toute conversation longue.

### 🟧 F3 — Profile picture TLS handshake timeout (63×)

**Symptôme**
```
log_context.go:117] Cache(peopleInfo): Singleflight refresh failed:
  failed to get profile picture:
  Get "https://lh3.googleusercontent.com/a/ACg8ocKbW8Ch8AKnIKUFiQStWl8c6d9d7QDWZiUKUHPKnYNPqwmG4w=s96-c":
  net/http: TLS handshake timeout
```

**Plage** : 14:45:40 → 14:47:57 (≈ 2 min 17 s, 63 occurrences).

**Cause** : Google people API (CDN `lh3.googleusercontent.com`) inaccessible. Le singleflight cache re-essaye en boucle, générant du spam.

**Mitigation possible** : circuit breaker local (TTL négatif) ou backoff exponentiel après N échecs.

## 5. Recommandations (par priorité)

### P0 — Immédiat
1. **Restaurer la connectivité** vers `172.217.16.46:443` (proxy / firewall / VPN).
2. **Purger le cache** LS pour forcer un refetch propre :
   ```powershell
   Remove-Item "$env:APPDATA\Antigravity\logs\*.log" -Force
   Remove-Item "$env:APPDATA\Antigravity\cache\*.cache" -Force
   ```
3. **Vérifier** `proxy-runner.js` et `start_mitm_443.ps1` — le relay local répond (`localhost:50999` OK) mais le saut vers Google échoue.

### P1 — Court terme
4. **Modèles placeholders** : ajouter dans `customModelStore.ts` (ou fichier de registry) un mapping `MODEL_PLACEHOLDER_M{35,36,50,71}` → IDs réels. S'inspirer de `antigravity-preload-duplication.md` (référence → callsite).
5. **Singleflight cache** :.backoff exponentiel sur `peopleInfo` (évite les 63 retries synchrones).
6. **Circuit breaker** sur F1 (5 échecs consécutifs → pause 60 s).

### P2 — Moyen terme
7. **Trajectoires dédoublonnées** : logger le pathsource du 2ᵉ load (race condition).
8. **Atomic rename annotations** : retry avec `os.RetryOnAccessDenied` ou flag antivirus exclusion sur `%APPDATA%\Antigravity\annotations`.
9. **Réduire la verbosité** `CDP Discovery` (debug-level plutôt qu'info) — divise le log par 2.
10. **Heartbeat du language server** : journaliser un `process_uptime` toutes les 5 min pour détecter les crashes silencieux (cf. F8).
